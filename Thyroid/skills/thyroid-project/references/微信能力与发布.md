# 微信能力与发布

## 作用

本文件定义甲状腺项目的微信外部能力配置检查和正式发布流程。通用的模板字段类型、长度、精度和格式门禁使用系统级 `wechat-miniprogram/references/微信能力与发布检查.md`；本文件只补充本项目的配置项、人工节点和发布顺序。

## 微信能力配置

当前项目涉及的订阅消息能力至少包括：

- 复查提醒：服务端对应的复查模板配置；
- 用药提醒：旧模板与新模板分别配置，并按提醒记录的模板版本选择；
- 版本更新通知：独立的版本更新模板配置和发送队列。

检查时只报告“已配置 / 缺失 / 不匹配 / 未启用”，不要输出模板秘密之外的 AppSecret、Token、openid 或其他凭据。模板 ID 本身是否需要在用户可见输出中展示，以当前任务是否必要为准。

新增或更换模板时先验证正常值、边界值和历史兼容值能否完整放入微信字段。剂量等有业务含义的数值不得通过静默截断或删除关键单位来适配新模板；旧模板历史兼容可以继续保留既有分支，但不能作为新模板设计依据。

## 功能就绪检查

### 开发/合并前

只做静态检查，不访问生产。先执行：

```powershell
& '.\tools\release\check-wechat-config.ps1'
```

该脚本只核对客户端模板常量、服务端 `.env.example` 的必需键和项目当前模板 ID 是否一致，不读取生产运行配置，也不输出模板 ID。随后继续人工/代码检查：

- 模板字段映射、长度与精度是否通过；
- 调度器/发送器代码和测试是否覆盖本次能力；
- 新能力的隐私与微信后台配置是否需要更新。

静态检查通过只证明仓库契约完整，不代表生产运行时已经配置。

### 正式发布流程

正式发布前做运行就绪检查；只有用户授权对应目标环境时才读取远端状态。重点防止：

- 客户端入口已经可见，但服务端缺少模板配置；
- 服务端进程正常，但对应 dispatcher/queue 没有启用；
- 新旧模板只配置了一种，却存在需要另一种模板的历史记录；
- 示例文件存在配置，但实际运行进程没有加载；
- 版本通知功能存在，但正式发布触发链路不可用。

本版本依赖的必需能力缺失时，停止正式发布；明确禁用的可选能力可以标记为“禁用”。

## 正式发布顺序

默认顺序：

```text
发布前静态检查
→ 用户分别授权微信代码上传与体验版动作
→ 体验版与人工验收
→ 用户在微信后台人工提审
→ 等待用户反馈“审核通过”
→ 判断本版本是否需要生产服务端 / 配置部署
   ├─ 不需要：继续
   └─ 需要：列出具体部署范围并等待用户明确授权
→ 获授权后部署并验证生产服务端 / 配置
→ 执行发布就绪运行检查
→ 等待用户明确授权正式发布
→ 正式发布
→ 核对正式版本实际生效
→ 如项目存在版本更新通知能力，询问用户是否发送
```

规则：

- Agent 不代替用户执行微信“提审”。
- 微信代码上传与体验版动作分别按用户明确授权推进；完成体验版不等于获准提审或正式发布。
- 审核通过后，如果本版本需要服务端、迁移或运行配置变更，Agent 必须先告诉用户“需要部署什么”，等待明确授权，不能因为审核通过自动部署。
- 正式发布需要独立授权；生产部署成功也不自动授权正式发布。
- 如果微信审核必须依赖新的线上服务能力才能完成，应在提审前明确说明并单独请求部署授权，不能静默改变默认顺序。

## 版本公告

- `docs/版本.md` 是公告内容来源；客户端的 `miniprogram/config/version-history.ts` 或等效文件应与其同步。
- 发布前核对版本号、公告条目和客户端构建数据一致。
- Git 合并、Tag、服务器版本元数据更新、体验版和审核通过都不能代替“微信正式版本已发布”的事实。

## 正式发布后的版本通知

只有同时满足以下条件才出现询问：

1. 本次流程已经确认微信正式发布成功；
2. 项目当前确实存在版本更新订阅通知能力；
3. 本版本属于该能力约定的正式全量发布范围。

此时只询问：

> 本版本已正式发布，是否现在向已订阅用户发送版本更新通知？

- 用户确认：才执行受保护的发布确认/通知动作，并核对入队、sent/failed 等结果。
- 用户选择稍后或不执行：记录为未执行/待办，不自动触发。
- 只合并 main、只部署服务端、只上传体验版、仅审核通过或项目没有该能力时，不出现这个询问。
- 不通过删除发布事件、重建订阅或修改已成功记录来重复发送。
