# 甲状腺微信小程序项目导航

## 核心职责

按任务加载最少的项目上下文，不复制项目文档，也不重新定义通用微信小程序开发流程。

通用的需求拆解、Figma 实现、前后端开发、数据库迁移、1Panel 部署、安全边界和微信开发者工具 QA 使用系统级 `wechat-miniprogram` Skill；本 Skill 只补充甲状腺项目的资料与路径。

## 默认完整开发闭环

### 简短触发语

- 用户说“开始全流程”时，按完整测试环境闭环执行，并视为已授权测试环境 SSH、数据库备份/迁移、服务端部署、容器重启、健康检查和 `targeted` QA。
- “开始全流程”不包含体验版上传、提审或正式发布；正式发布仍需单独授权。若遇到 SSH 认证失败、密钥解锁、首次主机信任或缺失配置，暂停并报告具体阻断，恢复后从当前阶段继续。

- 用户明确要求“开始开发”“按开发流程完成”或“完成该功能”时，默认按本次影响范围推进完整测试环境闭环：需求与代码核对 → 前端/服务端实现 → 本地类型检查、测试和生产构建 → 测试数据库历史迁移核对与备份 → 数据库迁移 → 测试服务端部署、回滚准备和应用/数据库健康检查 → 开发者工具定向 QA（`targeted`）→ 更新开发记录；不涉及的层级标记为“不适用”。
- 只有用户明确提出“只诊断”“只改前端”“仅本地验证”“跳过数据库迁移”或“跳过服务端部署”等范围时，才跳过对应环节，并在交付中记录未执行原因。
- 测试环境数据库迁移和服务端部署属于本项目完整开发流程的一部分；执行前仍必须遵守备份、历史迁移完整性核对、最小产物切换和失败回滚规则。
- 开发者工具 QA 默认使用 `targeted` 模式，至少覆盖本次功能的正常态、适用边界/空态、错误态和保存后回显；只有用户明确说“跳过 QA”或“跳过开发者工具 QA”时才豁免，并记录未执行范围。
- 自动 QA 通过不等于用户人工验收通过；人工验收状态必须单独记录。
- 小程序上传、提审和正式发布不属于默认测试闭环；功能开发期间不主动执行或反复提醒，只在开发记录的 TODO 中保留。用户之后明确要求进入发布流程并明确授权时，再单独建立发布清单，并在实际上传、提审和正式发布前按授权边界执行。

## 完整闭环推进与分支保留

- 用户确认开始开发后，立即建立本次影响范围的阶段清单，并为前端、服务端、数据库、部署、QA、文档分别标记“执行”“不适用”“未执行”或“阻塞”；不要用当前对话中的单个子步骤替代总目标。
- 没有阻塞时，按阶段清单自动推进到所有适用步骤完成；完成一个步骤后直接进入下一个未完成步骤，不因阶段性结果再次要求用户说“继续”。
- 只有密码或密钥解锁、首次主机信任、开发者工具确认、缺失且必须由用户提供的配置，或尚未获得的明确授权等真实阻塞点才暂停；用户解决阻塞后，从清单中的下一项自动继续。
- 用户临时提出“连接服务器”“只做迁移”等局部请求时，先执行该局部范围，同时保留总清单；如果用户明确缩小或替换原范围，再按新范围更新清单，并在交付中记录未执行项。
- A/B 策划分支、纯前端/已有服务端/需新增服务端分支、数据库迁移/服务端部署条件、`targeted`/`full`/`skip` QA 分支，以及未获授权时的边界继续按本 Skill 既有规则执行；自动推进不得跳过这些判断。
- 只有所有适用阶段完成、剩余项已明确标记为不适用、未执行、用户验收待进行或独立 TODO 后，才可以将阶段总结为完成；自动 QA 通过、容器处于 Up 状态或文档已更新，均不能单独代表整个阶段完成。

## 弹窗内部滚动规则

- 弹窗需要内部独立滚动时，使用 `page-meta` 在弹窗打开期间设置页面级 `overflow: hidden`，锁定背景页滚动。
- 不要在包含内部 `scroll-view` 的祖先遮罩上使用 `catchtouchmove` 或 `catchwheel` 作为背景锁定方案；祖先拦截可能同时阻止内部列表的触摸和鼠标滚轮滚动。
- 同一方向存在多个滚动区域时，活动弹窗分支只保留一个实际纵向滚动容器；必要时将外层表单改为普通容器，并为内部列表设置明确高度和 `scroll-y`。

## 开始任务

1. 读取仓库根目录 `AGENTS.md`；
2. 读取 `docs/开发记录.md` 的“当前状态”和“当前遗留事项”；
3. 根据任务类型继续读取下列唯一事实来源；
4. 检查相关代码、配置和实际脚本，不用文档替代代码事实；
5. 确认范围、排除项和成功标准；
6. 涉及新增功能或产品规则变化时，先完成策划关卡，再进入技术设计和编码。

### 策划关卡

按系统级 `wechat-miniprogram` 的 A/B 分支处理，不得从需求输入直接跳到前端或服务端编码：

- A（明确策划案和 Figma）：读取本项目三份事实文档、相关代码、接口和本地迁移，核对策划、Figma 与现有实现；集中提问并由用户确认修订后的策划；
- B（Figma 和模糊需求）：先读取同样的项目技术基线，再与用户共同形成草案；按草案深入检查相关模块，集中提问并由用户确认最终策划。

两条分支都在用户最终确认前检查技术可行性。确认后将规则写入 `docs/策划案.md`，再自主整理接口、数据迁移、前端、服务端、验证和部署方案；只有方案会改变产品行为、数据、安全、成本、授权范围或存在重大取舍时才再次询问用户。

用户明确要求只讨论策划案时，停在正式策划案确认与更新，不提前创建业务代码、接口或迁移。用户已经明确说“按已确认策划开始开发”时，可复核已确认内容后继续，不重复要求确认。

不要默认读取 `docs/archive/`。只有用户要求追溯历史、当前文档疑似遗漏或需要核对整理前原文时，才读取对应归档文件。

## 按任务读取

- 产品功能、交互规则或阶段策划：读取 `docs/策划案.md`；
- UI 视觉或交互任务：开始任务前先尝试读取 `docs/UI规范.md`；如果文件不存在或无法读取，则停止本次 UI 设计、实现或验收，不自行补写或替代该规范；仅做现状核对或文档整理时可继续，但需明确说明未读取；
- 接口、数据、鉴权、时区、架构或部署参数：读取 `docs/技术设计.md`；
- 当前完成状态、验收证据、历史经验或遗留事项：读取 `docs/开发记录.md`；
- Figma 或前端：检查 `miniprogram/`，并读取策划案中的对应规则和实际 Figma 节点；
- 服务端或数据库：检查 `server/src/`、`server/migrations/`、`server/tests/` 和服务端 `package.json`；
- 微信开发者工具 QA：读取 `references/微信开发者工具QA.md`，由系统级 `wechat-miniprogram` 编排官方 `wechatide-skill` 执行定向测试；用户明确选择 `full` 时才执行固定回归；
- 测试环境部署：读取技术设计中的部署基线，再按系统级 Skill 执行备份、迁移、部署、回滚与健康检查。

### 历史迁移完整性

对已有测试环境或正式环境执行数据库迁移、部署依赖数据库字段的服务端前，必须把本地 `server/migrations/` 的历史迁移按编号与目标库的实际表结构、索引或已记录迁移版本逐项核对；不得只确认本次新增迁移已执行。若当前服务端查询或写入的字段、索引来自历史迁移，也必须确认目标库已经具备。

发现遗漏时，先备份，再按编号顺序补执行全部缺失迁移；补后核验字段、索引和约束，再继续服务端部署或接口联调。将核对范围、缺失项、备份位置和结构核验结果写入开发记录；不得把应用 `/health` 成功替代为迁移完整性证明。

### MySQL 迁移字符集

对测试环境或正式环境执行 `mysql`、`mysqldump` 等远端 MySQL 客户端命令时，必须显式传入 `--default-character-set=utf8mb4`，不得依赖容器或客户端默认字符集。

包含中文标签、文案或其他非 ASCII 数据的迁移文件必须在数据写入前执行 `SET NAMES utf8mb4`；迁移后除核验表和字段字符集外，还要按固定业务键抽查实际文本或十六进制字节，确认没有发生乱码或二次编码。发现异常时先保留备份并新增修复迁移，不直接覆盖既有迁移历史。

## 项目入口

```text
miniprogram/          原生微信小程序 TypeScript
server/src/           Node.js/Fastify 服务端
server/migrations/    MySQL 数据库迁移
server/tests/         服务端自动化测试
automation/           微信开发者工具 QA
docs/                 当前有效项目文档
```

当前业务自然日统一使用 `Asia/Shanghai`。测试环境通过本机 SSH 隧道连接 ECS 上仅监听 `127.0.0.1:3000` 的服务；具体参数以技术设计和实际配置为准。

### 横屏 Canvas 与右侧控制栏

修改抽血横屏趋势页时，使用页面实际逻辑像素统一计算 Canvas 绘图区和右侧控制栏，不要让 WXSS 与 Canvas 分别维护互不关联的固定留白：

- 右栏宽度按窗口宽度约 15% 计算，并限制在 `108～128px`；按钮使用同一计算高度并限制在 `34～40px`；
- 把右栏宽度、右边距和最小间隔合成为 Canvas 的右侧预留，页面 `onResize` 时同时重算并重绘；
- 横屏窄控制栏优先使用受上下限约束的 `px`，不要只用随横向宽度放大的 `rpx`；
- 使用微信胶囊底部位置计算控制栏顶部，避免首个按钮被遮挡；
- 页面容器已经提供右侧内边距时，不要未经实测再次叠加 `safeArea.right`；开发者工具的横屏安全区可能造成重复留白；
- 在目标横屏分辨率读取实际计算值并截图，核对按钮等宽等高、图例不截断、最后一个数据点与右栏只保留必要间隔。

设计服务端字段、主键、外键和索引前，先读取技术设计、服务端代码和历史迁移。只有本地事实不足、冲突或疑似过期时，才询问用户是否允许只读检查测试环境数据库结构；获得允许后只读核对结构、索引和约束，不读取无关业务数据。

进入需要服务端的开发者工具 QA 前，按 `references/微信开发者工具QA.md` 先检查 `http://localhost:3000/health`。检查失败时，使用 SSH 配置别名 `thyroid-ecs` 自动启动隐藏后台隧道，再复查健康状态；不得读取、打印或写入别名背后的真实服务器地址和凭据。遇到密码、密钥解锁、首次主机信任或权限确认时停止自动处理，并立即向用户给出该参考文件中的两条人工命令，不要只报告“登录失败”或“服务端未连接”。

## 完成任务

- 首次运行前端或服务端命令前，检查实际 `package.json`、锁文件、项目脚本以及 `node`、`npm`、`pnpm` 的解析结果；不要假设当前 PowerShell 与上一轮任务具有相同 PATH；
- 若 `npm` 不在 PATH，但 Codex 工作区提供了独立 Node 或包管理器，使用已确认的绝对路径或项目现有包管理器继续；不得把微信开发者工具自带的 `node.exe` 默认为服务端工具链，也不得在尚有安全回退路径时直接宣布类型检查无法启动；
- 远端变更前执行代码 Review，以及与改动对应的类型检查、测试和生产构建；修复后复核受影响代码；
- 涉及数据库或部署时保留备份、历史迁移完整性核对、结构核验、回滚和健康检查证据；
- 开发者工具 QA 默认使用 `targeted` 模式；用户明确选择 `full` 时执行固定回归，选择 `skip` 时跳过开发者工具 QA；如实记录未执行范围，不得写成通过；
- `skip` 只跳过开发者工具 QA；本地 Review、类型检查、测试和构建仍按改动执行。只有用户明确要求跳过全部验证时才一并跳过，并记录风险；
- 纯小程序、本次不涉及服务端或数据库、没有远端环境、任务不需要部署或未获授权时，跳过对应层级并标记为“不适用”或“未执行”，不得主动扩建或连接远端；
- QA 前按 `references/微信开发者工具QA.md` 定义本次功能的前置条件、步骤、断言和截图点；使用官方 `wechatide-skill` 完成环境初始化、编译、页面自动化和调试取证；
- 同一失败层级最多自动修复并重测两轮；第二轮仍失败时停止，保留证据并说明唯一必要的下一步；
- 每轮 QA 在独立目录保存 `report.json`、日志和关键截图，维护 `latest.json` 并只保留最近三次完整运行；
- 产品规则变化更新策划案；
- 接口、数据或架构变化更新技术设计；
- 当前状态、验收结果和有效遗留事项更新开发记录；
- 自动 QA、用户人工验收和正式发布分别记录；用户未明确验收时只能写“用户验收待进行”；
- 删除账号属于不可恢复的数据操作，验证时应使用一次性测试账号；
- 交付总结前执行流程复盘，先列出通用规则、项目长期规则、一次性事故的可复用预防方法和不建议写入 Skill 的偶发现象；说明建议归属，由用户决定是否更新 Skill；
- 不在多份文档中重复同一段事实。
