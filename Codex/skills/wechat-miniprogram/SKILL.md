# 微信小程序全流程开发

## 核心规则

- 先按策划成熟度进入 A/B 分支，确认阶段需求、排除项、数据归属和成功标准，再修改代码。
- 先识别项目架构。没有服务端且需求未要求新增服务端时，只执行小程序前端与开发者工具 QA，不创建服务端、数据库、SSH、1Panel 或部署内容。
- 遵循项目 `AGENTS.md`、策划案、技术文档、Figma 和现有代码规范。
- 默认推进完整闭环，不在前端或本地构建完成后提前停止。
- 每一层验证通过后再进入下一层；失败时先定位层级，再做最小修复。
- 首次执行 Node.js 命令前检查项目脚本、锁文件和当前环境对 `node`、`npm`、`pnpm` 的实际解析；不要假设不同会话具有相同 PATH。`npm` 缺失时使用项目现有包管理器或已确认的工作区绝对路径，不把微信开发者工具自带的 `node.exe` 默认为项目服务端工具链。
- 开发者工具 QA 使用官方 `wechatide-skill` 执行；系统级 `wechat-miniprogram` 负责编排测试范围、模式、失败止损和证据，不重复实现开发者工具控制能力。
- 手机真机调试涉及本地服务端或 SSH 隧道时，先读取 `references/故障排查.md` 的“手机真机调试与局域网服务端”并完成局域网、监听、`/health` 和 API 地址前置检查，再调用官方 `wechatide-skill` 开启真机调试；结束后关闭真机调试并恢复 API、隧道和临时防火墙配置；模拟器可访问不等于手机真机可访问。
- QA 默认使用 `full`（本功能定向测试 + 项目固定回归）；用户可明确选择 `targeted`（仅定向测试）或 `skip`（跳过开发者工具 QA）。未执行部分标记为“未执行/用户豁免”，不得声明通过。
- 不输出 AppSecret、密码、私钥、Token、openid 或完整公网 IP。
- 测试环境与正式发布分开；上传、提审和正式发布必须另行获得明确授权。

## 引用路由

按任务读取引用文件，不把细节堆入主文件：

- 所有阶段任务：`references/需求与阶段策划.md`、`references/技术实践与安全边界.md`；
- Figma 或前端实现：`references/Figma与前端实现.md`；
- 项目已有服务端或需求明确新增服务端时：`references/服务端与数据设计.md`；
- 项目已有远端部署链路且任务明确涉及部署时：`references/Codex远程部署操作.md`；
- 微信开发者工具或 QA：`references/微信开发者工具自动化QA.md`；
- 任意错误或连续失败：`references/故障排查.md`。

如果任务需要调用 Figma `get_design_context`，同时加载会话中可用的 `figma-design-to-code` Skill，并遵循其强制要求。

执行开发者工具 QA 时，必须先读取项目的 QA 规则和用例，再按引用文件调用官方 `wechatide-skill`；同一失败层级最多自动修复并重测两轮，不得无限重试。

## 强制交付流程

先按 `references/需求与阶段策划.md` 处理策划关卡：

- A 分支：用户提供明确策划案和 Figma 时，读取项目技术事实，核对冲突并集中提问；用户确认修订后的策划案后进入开发；
- B 分支：用户只提供 Figma 和模糊需求时，先读取项目技术基线，与用户共同形成策划草案，再按草案深入检查技术可行性；用户确认最终策划案后进入开发。

两条分支都必须在用户确认前读取技术文档、相关代码、接口和本地迁移，尽量提前发现冲突。策划确认后自主完成技术设计；只有方案会改变产品行为、数据、安全、成本、授权范围或存在重大取舍时才再次询问用户。

策划确认后，检查仓库目录、配置、接口调用和项目文档，将项目分类为：

- 纯小程序：数据仅在页面状态、本地存储、微信原生能力或已接入的托管能力中处理，仓库没有自建服务端；
- 已有服务端：仓库或文档存在自建 API、数据库、部署目录或远端环境；
- 需要新增服务端：当前没有服务端，但用户需求明确要求跨设备持久化、服务端鉴权、集中数据或远端接口。

不要仅因 Skill 支持全栈，就为纯小程序主动新增服务端。若无法从仓库与需求判断且选择会显著扩大范围，再向用户确认。

按以下顺序连续推进，标注“条件执行”的步骤不适用时直接跳过：

1. 完成 A/B 策划关卡，将确认规则写入正式策划案；
2. 自主确定前后端职责、API、数据契约、迁移、测试、部署和回滚方案；
3. 读取具体 Figma 节点，编写原生小程序前端；
4. 条件执行：仅在“已有服务端”或“需要新增服务端”且本次涉及对应层级时，编写服务端、数据库迁移和自动测试；
5. 执行远端变更前的本地关卡：代码 Review、相关类型检查、自动测试和生产构建；修复后复核受影响代码；
6. 条件执行：仅在项目存在远端部署链路、本次确实需要部署且已获授权时，执行备份、迁移、部署、结构核验、健康检查和回滚准备；
7. 条件执行开发者工具 QA：确认 `full`、`targeted` 或 `skip`，调用官方 `wechatide-skill` 完成环境门禁、编译、用例、日志与截图取证；
8. 根据 QA 证据做最小修复并重跑失败及相邻用例；同一失败层级第二轮仍失败时停止，报告证据、已尝试动作和唯一必要的下一步；
9. 更新策划案、技术设计和阶段开发记录，区分自动验证、用户人工验收与正式发布；
10. 执行流程复盘，先向用户列出可复用知识候选及建议归属；只有用户同意后才写入 Skill；
11. 向用户汇总已通过层级、未执行层级、遗留人工验收和正式发布差距。

条件执行规则：

- 纯小程序不创建服务端、数据库、SSH、1Panel 或部署内容；
- 本次不涉及服务端或数据库时，对应开发、测试和部署标记为“不适用”；
- 没有远端环境、任务不需要部署或未获授权时，停在本地验证结果；
- `skip` 只跳过开发者工具 QA，不默认跳过代码 Review、类型检查、自动测试和构建；只有用户明确要求跳过全部验证时才一并跳过并说明风险；
- 自动 QA 通过不等于用户人工验收通过；用户未确认时只能记录“用户验收待进行”。

不得把“代码已写完”“测试通过”“容器 Up”或“模拟器截图正常”单独宣布为整个阶段完成。

## 验收关卡

- 设计关：具体 Figma 节点已读取，用户规则与设计差异已记录；
- 前端关：类型检查通过，空态、已设置、边界和错误状态可复现；
- 服务端关（适用时）：鉴权、校验、接口和迁移有自动测试，生产构建通过；
- 数据关（适用时）：迁移前有备份，目标表结构只读核验通过；
- 部署关（适用时）：旧版本可回滚，应用与数据库健康检查通过；
- QA 关：所选模式要求的开发者工具用例通过，无未处理控制台或网络错误，关键状态有截图；豁免部分单独记录；
- 交付关：文档与实际状态一致，人工验收和正式发布状态单独说明。

## 阻塞边界

- 首次登录开发者工具、扫码、CLI 授权、项目确认、微信授权和真机确认可要求用户完成一次；完成后继续自动流程。
- 缺少明确的数据库或部署授权时，停在本地验证结果，不擅自操作远端。
- 缺少具体 Figma 节点时，先从文件元数据定位；仍无法确定且会显著改变 UI 时再询问。
- 预览二维码、上传体验版、提审和发布属于外部变更，不因“完成开发”自动获得授权。

## 输出要求

- 使用中文，明确本次读取和使用的 Skill。
- 命令注明 Windows PowerShell、微信开发者工具、ECS、MySQL 或 1Panel。
- 每阶段报告目的、动作、预期结果与验收证据。
- 只声明有证据支持的完成状态。
