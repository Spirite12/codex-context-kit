# 微信小程序全流程开发

## 核心规则

- 先判断任务类型，再决定需要哪些关卡；不要把所有任务都强制套入“策划 + Figma + 全栈部署”。
- 新增功能或改变产品行为时先确认范围、排除项、数据归属、成功标准，以及适用的主类、隐私或平台能力影响；已确认方案的实现、明确缺陷修复、环境切换、配置核对和纯文档任务不重复要求产品确认。
- 先识别项目架构。没有服务端且需求未要求新增服务端时，不创建服务端、数据库、SSH、1Panel 或部署内容。
- 项目 `AGENTS.md`、项目 Skill、项目事实文档和实际代码优先于本 Skill 的通用默认；项目 override 不得削弱用户授权、安全和证据真实性。
- 本地开发、隔离测试和生产环境分开。网络连通问题不能通过静默切换数据环境解决；健康检查成功也不能单独证明目标环境身份。
- 外部微信能力（如订阅消息、广告、支付、隐私权限）在实现时检查字段和平台约束，在进入发布流程时检查实际运行配置是否就绪；“代码已接入”不等于“线上能力可用”。
- 开发者工具 QA 使用官方 `wechatide-skill`；本 Skill 只编排范围、模式、失败止损和证据。
- QA 默认使用 `full`，项目可明确覆盖为 `targeted`；`skip` 仅在用户或项目规则明确允许时使用。未执行部分不得写成通过。
- 不输出 AppSecret、密码、私钥、Token、openid、数据库连接串或完整公网 IP。
- Git 合并、服务端部署、微信上传、体验版、提审和正式发布是不同阶段；任何远端或发布写操作都只在用户当前授权范围内执行，不自动扩大到后续阶段。

## 任务分类

开始前先归类；一个任务可以命中多个类型，但不要因此自动扩大范围：

1. **新增功能 / 产品行为变化**：执行产品策划关卡，再进入技术设计与实现。
2. **已确认方案的实现**：复核已确认规则和代码现状，直接进入实现；只有新发现会改变产品、数据、安全、成本或授权范围时再询问。
3. **明确缺陷修复**：先复现和定位，做最小修复；若修复需要改变原产品行为，转入第 1 类。
4. **环境 / 配置 / 联调**：先确认目标环境与连接方式；不强制要求 Figma 或产品策划，除非会改变用户行为或数据处理。
5. **QA / 部署 / 发布准备**：读取项目已有规则和实际配置，只推进到用户授权的阶段。
6. **纯文档 / Skill / 流程整理**：核对事实来源和职责边界，不运行与改动无关的业务验证。

## 开发闭环

对适用层级按顺序推进：

1. 确认任务类型、范围、排除项和成功标准。
2. 按需读取项目事实文档、代码、配置、迁移和测试，不用旧对话替代当前仓库事实。
3. 新增功能或产品行为变化时完成策划关卡；其他类型按任务直接进入对应阶段。
4. 明确前端、服务端、数据、微信外部能力和环境依赖，只实现本次需要的部分。
5. 完成代码 Review、相关类型检查、自动测试、构建或静态验证。
6. 涉及微信外部能力时，先验证模板/字段等设计契约；进入发布流程时再执行目标环境的功能就绪检查。
7. 仅在项目存在远端链路、本次确实需要且已获授权时执行数据库或服务端变更，并保留回滚和验证证据。
8. 按项目选择的 `full`、`targeted` 或 `skip` 执行开发者工具 QA；失败只修当前层级的最小问题，同一失败层级第二轮仍失败时停止。
9. 更新项目规定的事实文档，区分实现完成、自动验证、真机/人工验收和正式发布。
10. 如果用户进入发布流程，按项目定义的人工节点和授权边界继续；不要因为前一阶段成功自动执行下一项外部写操作。

## 微信能力与发布就绪

- 新增或更换订阅消息模板等平台能力时，先核对业务数据是否能在平台字段类型、长度、精度、格式和枚举约束内无损表达；不能无损表达时停止，不通过截断数值、删除有意义单位等方式静默兼容。
- 开发或合并前可以做静态配置完整性检查，但不得因此连接生产。
- 正式发布流程中的功能就绪检查，只有在项目规则和用户授权允许访问目标环境时执行；检查配置是否存在时只报告“已配置/缺失/不匹配”，不打印秘密值。
- 项目若定义正式发布后的通知、批处理或公告动作，发布成功后按项目规则询问或执行；部署成功本身不授权这些后续动作。

## 验收与输出

- 设计/产品关：已确认本次用户可见行为和排除项。
- 前端关：相关类型检查或编译通过，关键状态可复现。
- 服务端/数据关（适用时）：鉴权、校验、迁移和自动测试覆盖本次变化。
- 微信能力关（适用时）：字段契约和本次发布所需运行配置可核验。
- QA 关：所选模式要求的用例通过，没有未处理错误；未执行项单独记录。
- 发布关（适用时）：只声明实际完成且可核验的上传、审核、部署或正式发布状态。

最终回复保持简洁：报告实际结果、必要的核心标识，以及阻塞或用户可能误认为已执行但实际未执行的关键后续动作。
