# 微信开发者工具 QA

## 职责边界

- `wechat-miniprogram` 负责选择 QA 模式、定义验收范围、控制修复轮次和汇总证据；
- 官方 `wechatide-skill` 负责开发者工具环境、编译、模拟器操作、页面自动化、console/network 和截图；
- 项目 `AGENTS.md`、项目 Skill 或 `automation/` 内的 QA 文件负责业务用例、固定回归和产物位置；
- 不把项目业务规则写入官方 Skill，也不重复维护一套通用 CLI/端口控制代码。

如果官方 Skill 不可用，先按其 `installer` 或环境诊断流程处理。旧 `cli.bat`、`miniprogram-automator` 或项目 QA 脚本只作为已有项目的迁移回退；除非用户明确同意，不自动切回旧流程。

## QA 模式

| 模式 | 范围 | 规则 |
| --- | --- | --- |
| `full` | 本功能定向测试 + 项目固定回归 | 默认 |
| `targeted` | 仅本功能定向测试 | 用户明确要求不跑回归时 |
| `skip` | 不进入开发者工具 QA | 用户明确要求跳过时 |

`targeted` 和 `skip` 的未执行部分必须记录为“未执行/用户豁免”，不得写成通过。涉及登录、公共组件、公共请求层、首页状态或数据契约的高影响改动，在接受豁免前说明风险。

## QA 前置

1. 完成本次改动对应的本地类型检查、自动测试和生产构建；
2. 涉及服务端联调时，先执行项目规定的 Windows 侧健康检查；若失败且项目提供了可逆、安全的本地隧道命令，则使用项目记录的 SSH 别名自动启动隐藏后台隧道并再次检查，不打开多余可见终端；
3. 读取项目 QA 规则、固定回归清单和已有测试数据说明；
4. 确认 QA 模式；用户没有特别指定时使用 `full`；
5. 定义本功能用例的目标、前置条件、步骤、断言、截图点和数据影响；
6. 涉及覆盖真实测试数据、签到、授权、上传或其他外部变更时，先取得对应授权。

自动建立隧道时只使用项目明确记录的 SSH 别名、本地端口和目标回环地址，不把真实公网地址、账号、密码、密钥或 Token 写入 Skill、命令回显和 QA 产物。若命令需要密码、首次主机信任、密钥解锁或额外权限，立即停止自动重试，并在首次报告中直接给出项目规定的隧道命令和健康检查命令，说明需要用户完成的唯一动作；用户完成后继续当前 QA。

## 本功能定向测试

至少定义并执行：

```text
用例 ID：稳定且可追踪
目标：本次功能要证明的结果
前置条件：登录态、页面、服务端与测试数据
步骤：用户可复现的顺序操作
断言：页面、接口、数据回显和错误状态的通过标准
截图点：关键状态与失败时最后画面
数据影响：无 / 复用现值 / 新增或覆盖
```

覆盖正常态，以及适用的空态、边界态和服务端错误态。持久化功能应验证保存后重新进入回显。无法稳定构造的状态应记录为未执行或人工验收，不得虚构通过。

## 固定回归

仅在 `full` 模式执行项目维护的固定回归清单：

- 优先执行不破坏真实测试数据的核心路径；
- 本次改动触及的保存逻辑放入定向测试，固定回归默认复用现有有效值；
- 需要覆盖数据或触发不可逆业务状态时先取得授权，并记录最终数据；
- 定向测试修复后，重跑失败用例、相邻用例，再执行固定回归。

项目没有固定回归清单时，不临时猜测整套回归。先根据产品事实来源建立最小核心清单，再执行并留证。

## 官方 Skill 执行顺序

1. 加载 `wechatide-skill` 根入口并遵守其运行前门禁；
2. 首次预期出现客户端连接授权弹窗却未出现时，不连续等待多轮超时：先确认开发者工具已启动并检查“设置 → 安全设置 → 服务端口”；能安全代设时先询问用户是否允许，不能代设时立即给出操作路径，用户处理后只重试连接门禁；
3. 使用 `initializer` 检查版本与登录状态、打开项目并读取运行时上下文；
4. 使用 `compiler` 编译或刷新目标页；触发刷新成功不等于编译通过；
5. 使用 `automator` 完成页面导航、点击、输入、滚动、数据读取、断言和自动化截图；
6. 使用 `debugger` 收集 console、network、运行时和模拟器截图，检查未处理异常；
7. 跨 scene 时按官方 Skill 的移交格式传递项目路径、已确认事实、当前页、选择器、阻塞和异步任务；不要重复门禁或无故重开窗口；
8. 汇总所选 QA 模式的结果并写入项目规定的证据目录。

开发者工具“服务端口”是 CLI 接入开关，不是项目 API 端口。沟通和报告必须明确区分。

预览、上传体验版、提审和正式发布不属于开发完成后的默认 QA。只有用户单独授权时才进入 `previewer` 或发布流程。

## 有限修复与失败止损

将失败归类为：

1. `environment`：版本、登录、令牌、授权或项目窗口；
2. `compile`：编译、依赖或模拟器刷新；
3. `automation`：页面路径、选择器、等待或交互；
4. `network`：隧道、合法域名、请求或服务健康；
5. `business`：前端、接口、数据或业务断言；
6. `evidence`：日志、截图或报告不完整。

第一次失败后只修复当前层级的最小问题，重新执行失败用例及相邻用例。同一失败层级第二轮仍失败时立即停止；不要继续重启、重连、延长等待或猜测修改。输出失败步骤、最后成功步骤、证据、已尝试修复和唯一必要的下一步。只有用户明确要求继续或提供新信息后，才开始新一轮。

官方 Skill 返回 `pending + taskId` 时遵循其异步任务规则，不重复提交原操作。首次扫码登录、授权或真机操作只请求用户完成当前一步。

## 日志、截图与报告

每轮使用独立时间目录，至少保存：

```text
report.json
console.log
network.log
screenshots/
```

`report.json` 至少包含：QA 模式、功能范围、用例结果、未执行/豁免项、失败层级、数据影响、开始结束时间和证据路径。成功与失败运行都生成报告；只有所选模式要求的用例全部通过、没有未处理错误且关键截图有效时，才将 QA 标记为通过。

截图前等待目标数据和节点稳定；自动化步骤截图使用 `automator`，含 Toast 或完整模拟器 UI 的诊断截图使用 `debugger`。生成截图后应人工查看关键图片，不以文件存在代替视觉验收。

每个测试范围维护 `latest.json`，默认只保留最近三次生成了 `report.json` 的完整运行。删除必须限制在当前项目对应的 QA 产物目录，不得清理代码、附件或其他测试套件。

## 人工边界

- 首次扫码登录、CLI 授权、项目确认、微信授权和真实账号确认；
- 真机字体、安全区域、键盘、弱网和触感；
- 预览二维码扫码、上传、提审与正式发布。

需要用户操作时只请求当前一步；完成后继续当前 QA，不把剩余验证整体退回给用户。
