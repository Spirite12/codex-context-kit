# 需求与阶段策划

## 开始前读取

优先读取项目中的策划案、技术设计、上一阶段记录、当前阶段记录、接口文档和 `AGENTS.md`。记录实际文件路径，不依赖对话记忆替代项目文档。

## 策划分支

### A：明确策划案和 Figma

1. 读取用户策划案、Figma、现有策划、技术设计和阶段记录；
2. 定向读取相关代码、接口、本地数据库迁移和配置；
3. 核对策划、Figma 与现有实现的矛盾、遗漏和技术约束；
4. 集中提出需要用户决定的问题；
5. 用户确认修订后的策划内容，再写入正式策划案。

不要要求用户确认普通实现细节。策划确认后，自主确定文件组织、API 拆分、索引、事务和测试方式；只有技术方案会改变产品行为、数据、安全、成本、授权范围或存在重大取舍时才再次询问。

### B：Figma 和模糊需求

1. 读取用户输入、Figma、现有策划、技术设计和阶段记录；
2. 定向读取相关代码、接口、本地数据库迁移和配置，建立现有能力与限制基线；
3. 与用户共同整理包含范围、排除项、交互状态、数据归属、边界和成功标准的策划草案；
4. 根据草案涉及的模块，深入核对前端、服务端、数据库、鉴权、时区、安全、测试和部署影响；
5. 集中提出剩余冲突和需要用户决定的问题，修订草案；
6. 用户确认最终策划案，再写入正式策划案。

两次技术读取深度不同：草案前读取项目基线，避免策划脱离现有系统；草案后按具体影响深入检查，避免遗漏。确实无法提前发现的新事实，在 A/B 两条分支都按影响程度处理：不改变已确认产品规则的技术问题自主解决；影响产品、数据、安全、成本或授权时再询问用户。

## 架构范围判断

先检查仓库是否存在服务端源码、服务端依赖清单、API 路由、数据库迁移、Docker/1Panel 配置或明确部署文档，并检查小程序是否调用自建远端 API。

- 没有上述证据且需求只涉及页面、本地状态或本地存储：按纯小程序处理；
- 已存在自建 API 或数据库：按已有服务端处理，但只修改本阶段直接涉及的部分；
- 当前没有服务端，只有用户明确要求跨设备持久化、集中数据、服务端鉴权或新建远端接口时，才提出新增服务端方案。

纯小程序项目不得自动创建 `server/`、数据库迁移、Docker 配置、SSH 隧道或 1Panel 操作。阶段文档中将这些层级标记为“不适用”，而不是“未完成”。

本次不涉及已有服务端或数据库时，也将对应层级标记为“不适用”。没有远端环境、任务不需要部署或未获授权时，只完成本地设计与验证，不连接远端。

## 将需求转换为规则

至少确认：

- 当前阶段包含与不包含的功能；
- 用户入口、空态、已设置状态和保存反馈；
- 默认值、最小值、最大值、步长、日期和时区；
- 单配置覆盖还是保留历史；
- 前端显示值由前端计算还是服务端返回；
- 登录、鉴权和未授权行为；
- 是否需要 Figma、服务端、数据库、1Panel 和自动 QA；服务端与 1Panel 必须有仓库证据或明确需求，不能按默认全选；
- 哪些动作需要用户扫码、授权或最终确认。

将模糊词转换为可断言行为。例如“立即覆盖”应落为单用户单行或明确更新语义；“明天开始”应由前后端同时拒绝今天及过去日期。

## 阶段文档

开发前记录需求边界和待确认项；开发后记录：

- 实现文件和接口；
- 数据库迁移（适用时）；
- 自动测试数量；
- 测试环境部署证据（适用时）；
- 开发者工具 QA 证据；
- 尚未完成的人工、真机和正式发布事项。

用户改变阶段顺序时，同步更新策划案、技术设计和阶段交接，不让旧范围继续影响实现。

## 流程复盘

自动 QA 完成、跳过或阻塞后，交付总结前都执行一次简短复盘。先列候选，不直接修改 Skill：

- 通用且可复用的流程规则；
- 项目长期有效的规则；
- 一次性事故及其可复用预防方法；
- 不建议写入 Skill 的偶发现象。

排查耗时、Token 消耗高、可能复发、原因隐蔽或涉及数据与安全的一次性事故也应提出。事件经过写项目记录或 QA 报告；提炼后的预防方法才作为 Skill 候选。说明建议归属和维护成本，由用户决定是否加入。
