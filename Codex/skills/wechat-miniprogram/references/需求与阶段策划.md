# 任务分类与需求策划

## 开始前

读取项目 `AGENTS.md`、项目 Skill 和与当前任务直接相关的事实文档、代码、配置、迁移与测试。不要默认读取整套历史记录，也不要用对话记忆替代当前仓库事实。

## 先分类任务

### 1. 新增功能或改变产品行为

需要确认范围、排除项、数据归属、用户入口、状态、失败行为和成功标准。项目存在主类、隐私或平台能力门禁时先执行这些判断。

若已有明确策划与 Figma：
1. 核对策划、Figma、现有实现和技术约束；
2. 集中提出真正需要用户决定的冲突；
3. 用户确认后更新正式策划，再进入实现。

若需求仍模糊：
1. 先读取项目技术基线；
2. 与用户形成最小可执行草案；
3. 深入检查前端、服务端、数据、鉴权、时区、安全、测试和发布影响；
4. 集中确认剩余产品决策，再进入实现。

不要要求用户确认普通实现细节。只有技术方案会改变产品行为、数据、安全、成本、授权范围或存在重大取舍时才再次询问。

### 2. 已确认方案的实现

复核正式策划、技术事实和代码即可进入实现，不重复进行完整策划。若实现中发现会改变已确认规则的新事实，再回到产品确认。

### 3. 明确缺陷修复

先复现、定位和确定影响范围，再做最小修复。修复保持原产品语义时不要求重新策划；若必须改变产品行为或数据规则，转为“新增功能或改变产品行为”。

### 4. 环境、配置和联调

先确认目标环境、连接方式、数据归属和允许动作。环境问题不强制要求 Figma；网络故障不得通过静默切换到另一数据环境解决。

### 5. QA、部署和发布准备

先确定用户要推进到哪个阶段，以及哪些远端或平台动作已授权。只补齐到目标阶段，不因为“全流程”字样自动取得生产写入、上传、提审或正式发布权限。

### 6. 文档、Skill 和流程整理

核对事实来源与职责边界；长期规则放 AGENTS/Skill，项目事实放项目文档，可执行且脆弱的重复步骤优先使用脚本。不要为了整理文档运行无关业务流程。

## 架构范围判断

检查仓库是否存在服务端源码、依赖清单、API 路由、数据库迁移、部署配置或明确远端架构，并检查小程序是否调用自建 API。

- 没有服务端证据且需求只涉及页面、本地状态、微信原生能力或既有托管能力：按纯小程序处理。
- 已存在自建 API 或数据库：按已有服务端处理，但只修改本次直接涉及的部分。
- 当前没有服务端：只有需求明确需要跨设备持久化、集中数据、服务端鉴权或新远端接口时，才提出新增服务端。

纯小程序不得自动创建服务端、数据库迁移、Docker、SSH 或 1Panel 内容。本次不涉及已有服务端或数据库时，将对应层级标记为“不适用”。

## 将需求转换为可验证规则

按任务适用范围确认：

- 包含与不包含的功能；
- 用户入口、空态、已设置态、加载/保存/失败反馈；
- 默认值、上下限、步长、日期、时区和幂等规则；
- 数据保存在客户端、服务端还是平台侧；
- 登录、鉴权和未授权行为；
- 是否依赖微信模板、权限、广告、支付或其他外部能力；
- 是否需要 Figma、服务端、数据库、远端部署和开发者工具 QA；
- 哪些动作必须由用户扫码、平台审核、最终确认或单独授权。

对微信外部能力，在产品规则确认后继续读取 `微信能力与发布检查.md`，把“平台字段是否能表达业务数据”和“发布时实际配置是否就绪”拆成两个检查阶段。

## 文档与复盘

产品规则写产品事实文档；接口、数据和架构写技术文档；未完成事项写待办；已经发生的结果只写必要证据和结论。

任务结束前可做简短复盘：把跨项目可复用的方法作为系统 Skill 候选，把项目长期规则作为项目 Skill/AGENTS 候选，把一次性事故留在项目记录或 QA 证据中。不要把实现参数和历史流水账重复搬进 Skill。
