# 新增功能策划与架构范围

## 开始前

本文件只处理“新增功能 / 产品行为变化”的策划关卡。已确认方案实现、明确缺陷、环境/配置、QA/发布和纯文档任务按主 Skill 的任务分类直接进入对应阶段；只有它们重新改变产品行为时才回到这里。

先读取项目 `AGENTS.md`、项目 Skill，以及与本次需求直接相关的事实文档、代码、配置、迁移和测试。不要默认读取整套历史记录，也不要用对话记忆替代当前仓库事实。

## 按需求成熟度推进

### 需求与规则已经明确

适用于产品目标、用户行为、边界和成功标准已经足够清楚的需求；UI 任务若已有 Figma，同时核对 Figma，非 UI 任务不以“必须有 Figma”作为前置条件。

1. 核对正式策划、适用的设计稿、现有实现和技术约束；
2. 找出真正影响产品行为、数据、安全、成本或授权范围的冲突与遗漏；
3. 集中提出需要用户决定的问题；
4. 用户确认后更新正式策划，再进入技术设计与实现。

### 需求仍然模糊或规则不完整

1. 先读取项目已有产品与技术基线；
2. 与用户形成最小可执行草案，明确范围、排除项和成功标准；
3. 按草案深入检查前端、服务端、数据、鉴权、时区、安全、测试和发布影响；
4. 集中确认剩余产品决策；
5. 用户确认最终规则后更新正式策划，再进入技术设计与实现。

两种路径都要在最终产品确认前检查技术可行性。不要要求用户确认普通实现细节；只有技术方案会改变产品行为、数据、安全、成本、授权范围或存在重大取舍时才再次询问。

## 架构范围判断

检查仓库是否存在服务端源码、依赖清单、API 路由、数据库迁移、部署配置或明确远端架构，并检查小程序是否调用自建 API。

- 没有服务端证据且需求只涉及页面、本地状态、微信原生能力或既有托管能力：按纯小程序处理。
- 已存在自建 API 或数据库：按已有服务端处理，但只修改本次直接涉及的部分。
- 当前没有服务端：只有需求明确需要跨设备持久化、集中数据、服务端鉴权或新远端接口时，才提出新增服务端。

纯小程序不得自动创建服务端、数据库迁移、Docker、SSH 或 1Panel 内容。本次不涉及已有服务端或数据库时，将对应层级标记为“不适用”。

## 将需求转换为可验证规则

按任务适用范围确认：

- 包含与不包含的功能；
- 用户入口、空态、已设置态、加载/保存/失败反馈；
- 默认值、上下限、步长、日期、时区和幂等规则；
- 数据保存在客户端、服务端还是平台侧；
- 登录、鉴权和未授权行为；
- 是否依赖微信模板、权限、广告、支付或其他外部能力；
- 是否需要 Figma、服务端、数据库、远端部署和开发者工具 QA；
- 哪些动作必须由用户扫码、平台审核、最终确认或单独授权。

涉及微信外部能力时，在产品规则确认后读取 `微信能力与发布检查.md`，把“平台是否能表达业务数据”和“发布时实际配置是否就绪”拆成两个检查阶段。

## 文档与复盘

产品规则写产品事实文档；接口、数据和架构写技术文档；未完成事项写待办；已经发生的结果只写必要证据和结论。

任务结束前可做简短复盘：跨项目可复用的方法作为系统 Skill 候选，项目长期规则作为项目 Skill/AGENTS 候选，一次性事故留在项目记录或 QA 证据中。不要把实现参数和历史流水账重复搬进 Skill。
