## 1. 适用架构

该 Skill 同时适用于纯小程序和小型全栈项目。先判断架构，再选择链路。

纯小程序典型链路：

```text
需求/Figma → 小程序前端 → 本地状态或微信原生能力 → 微信开发者工具与自动化 QA
```

纯小程序没有自建服务端时，不执行数据库、SSH、ECS、Docker 或 1Panel 步骤。

自建服务端项目典型链路：

```text
开发测试：Figma/需求 → 小程序前端 → 微信开发者工具与自动化 → 本机 127.0.0.1 → SSH 隧道 → ECS 127.0.0.1 → Node.js → MySQL
正式生产：微信小程序 → 已备案 HTTPS 域名 → 反向代理 → Node.js → MySQL
```

若项目使用云开发、Serverless、Kubernetes、托管数据库或多机高可用，应先重新确认架构，不机械套用本流程。

## 2. 推荐组件

- Ubuntu 22.04：稳定、资料丰富；
- 1Panel：适合小规模项目管理容器、数据库和文件；
- Node.js + TypeScript：适合微信登录和 JSON API；
- Fastify：依赖较轻，适合 2 核 2G 起步环境；
- mysql2：成熟的 MySQL 驱动；
- 原生微信小程序：早期页面少时可避免引入额外框架。

这是一套合理的起步组合，不是唯一正确方案。优先遵循项目现有架构、LTS 支持范围和锁文件。

## 3. 数据库原则

- 业务服务使用独立业务账号，不使用 Root；
- 3306 不向公网开放；
- 阿里云安全组也不放行 3306；
- 同一 Docker 网络内用容器连接名；
- 迁移文件进入版本控制，执行前确认目标数据库；
- 备份必须包含定期恢复演练；
- 健康检查使用 `SELECT 1` 等轻量查询，不暴露数据库详情。

1Panel 只有“所有人(%)”权限时，只能在数据库端口不对公网暴露、业务账号权限受限的前提下作为阶段性选择。

## 4. 服务与健康检查

服务在容器内通常监听 `0.0.0.0:<端口>`；测试期宿主机映射到 `127.0.0.1:<端口>`。两者不是矛盾：前者让容器端口可被映射，后者限制宿主机只接受本地连接。

健康检查至少区分：

- 应用进程是否启动；
- 数据库是否可查询。

推荐成功响应：

```json
{"status":"ok","database":"ok"}
```

数据库失败时返回 503，但响应和日志均不得包含密码、连接串或 SQL 敏感数据。

## 5. 微信登录与会话

推荐流程：

1. 用户主动点击登录；
2. 小程序调用 `wx.login()` 获取一次性 code；
3. 服务端用 code、AppID 和 AppSecret 换取 openid；
4. 以 openid 查找或创建内部用户；
5. 生成高熵随机 Token；
6. 数据库只保存 Token 的 SHA-256 哈希；
7. 明文 Token 仅返回客户端一次；
8. 后续请求通过 `Authorization: Bearer <token>` 鉴权。

`userId` 是系统内部 ID，`openid` 是微信小程序用户标识，二者不能混为一个字段。AppSecret 永远不能进入小程序包。

验收 SQL 应以统计为主：

```sql
SELECT COUNT(*) AS userCount FROM users;
SELECT COUNT(*) AS activeSessionCount
FROM user_sessions
WHERE expires_at > CURRENT_TIMESTAMP;
SELECT COUNT(*) AS totalSessions,
       SUM(CHAR_LENGTH(token_hash) = 64) AS hashedSessions
FROM user_sessions;
```

## 6. 微信 JSON 请求契约

使用 `wx.request` 发送 `POST`、`PUT`、`PATCH` 或 `DELETE` 请求时，如果请求的 `content-type` 为 `application/json`，即使接口没有业务参数，也应显式传递空对象 `{}`，不要发送 `undefined` 或完全省略请求体。微信请求层可能默认使用 JSON Content-Type，仅删除显式请求头不能保证避开空 Body 错误。

优先在公共请求封装中统一规范化：

```ts
const requestData =
  options.data ?? (options.method === 'GET' ? undefined : {});
```

随后使用同一个 `requestData` 设置请求数据及对应请求头，避免各接口重复补丁。

## 7. 测试和生产边界

仅限开发测试：

- 微信测试号；
- SSH 隧道；
- API 使用 `http://127.0.0.1:<端口>`；
- 微信开发者工具关闭合法域名校验。

正式生产必须增加：

- 正式小程序账号；
- 已备案 HTTPS 域名和有效证书；
- 微信公众平台服务器域名；
- 重新启用合法域名校验；
- 反向代理、限流、日志脱敏、监控与告警；
- 非 Root 运行和最小权限；
- 数据备份、恢复演练及密钥轮换；
- 隐私政策、用户协议和医疗健康合规评估；
- 真机及发布版本验证。

## 8. 验收证据

每一层保留非敏感证据：

| 层级 | 合格证据 |
| --- | --- |
| 数据库 | `SHOW TABLES` 返回预期表 |
| 容器 | 状态 `Up` 且端口绑定符合预期 |
| 应用 | 日志无持续重启或模块缺失 |
| 健康检查 | ECS 本机 HTTP 200 且数据库正常 |
| 隧道 | 开发电脑同一健康检查成功 |
| 微信身份 | AppID 一致，code2Session 成功 |
| 业务登录 | 首次与重复登录行为符合设计 |
| 会话安全 | 总会话数等于 64 位哈希会话数 |

## 9. 已验证参考基线

甲状腺小程序第一至第三阶段实际验证过以下组合：

- ECS：Ubuntu 22.04、2 核 2G、1Panel；
- MySQL：8.4.10；
- Node.js：24.14.0；
- TypeScript、Fastify、mysql2；
- 服务端绑定 `127.0.0.1:3000`；
- SSH 隧道联调；
- 微信测试号真实登录；
- SHA-256 会话 Token 哈希；
- 用药配置数据库迁移前备份、迁移执行和表结构核验；
- 仅替换 `dist` 的最小部署及旧版本回滚备份；
- 开发者工具合法域名校验与本机 SSH 隧道故障分层；
- 复查提醒单用户单配置、固定 7 天应用内提醒和逾期空态；
- 微信开发者工具 CLI 的打开、预览和自动化命令探测；
- 30 项服务端自动化测试通过；
- 第二阶段应用、数据库、开发隧道与微信开发者工具人工联调通过。

此基线用于证明方案可行，不应取代对新项目依赖版本和资源占用的重新审核。
