## 全局偏好

1. 使用中文回答；
2. 编写文档时，使用中文输出；
3. 编辑代码文件时使用 UTF-8 编码；

## 对话回复约定

1. 回复时请明确告知使用者：本次使用了哪些 `Skill`；

## 工程行为准则

1. 编码前先确认需求边界。若存在歧义，应明确列出假设或提出澄清问题；不要在不确定时静默选择一种解释并继续执行。
2. 优先采用能解决问题的最小实现。不要为一次性逻辑新增抽象，不添加用户未要求的功能、配置项或复杂错误处理。
3. 修改范围必须能直接追溯到用户请求。不要顺手重构、格式化、删除或改写无关代码；若发现无关问题，可以在回复中说明，但不要擅自处理。
4. 对于非平凡任务，应先明确成功标准，并在完成后通过测试、构建、静态检查或可人工核对的结果进行验证。
5. 如果实现中产生了新的无用导入、变量、函数或文件，应清理这些由本次改动造成的残留；不要清理本次任务之前已经存在的无关死代码，除非用户明确要求。
6. 对已有项目进行修改时，优先遵循项目现有架构、命名、代码风格、测试方式和文档规范；不要因为个人偏好引入新的风格或工具。
7. 若用户请求本身可能导致明显的过度设计、风险扩大或维护成本上升，应主动说明权衡，并给出更简单的替代方案。

## Skill 文档处理约定

1. 当新增或安装新的 Skill 时，需检查同级的 `SKILL.md` 是否以英文为主。
   - 如果是英文，则在同级补充一份中文说明文档，文件名优先使用 `SKILL.zh-CN.md`。中文文档应忠实表达原文含义，尽量保持结构对应，必要时可补充简洁的中文说明。

## 多 Agent 调度

仅在满足以下任一条件时，启用多 Agent 调度：

1. 用户明确要求启用多 Agent；
2. 项目 AGENTS.md 明确规定可启用多 Agent 调度，且当前任务符合其中定义的触发条件。

### Agent 调度规范

每次发起多 Agent 调度时，在创建子 Agent 前 以及 回复时须输出：

【多 Agent 调度回执】

- 调度来源：用户启用 / 按项目规则；
- 调用模型：模型名称、effort；
- 任务分配：每个 Agent 处理的事项与简要目标；

当无法调度时，新增：

- 异常说明：如模型或 effort 不可用、并发名额不足，则说明具体原因及受影响任务；

注意事项：

1. 同一组文件在同一时间只允许一个 Agent 写入；不为占满并发而调用多 Agent。
2. 除非项目规则已明确指定降级方案，否则不得自动替换用户指定的模型或 effort。

### 子 Agent 生命周期

1. 子 Agent 完成任务后，主 Agent 先使用 `wait_agent` 获取最终结果并完成整合；确认不再继续使用时，调用 `close_agent` 关闭，以释放并发名额。
2. 同一功能阶段仍需连续处理时，不要立即关闭；优先使用 `send_input` 复用，阶段完成后再关闭。
3. 后续用户任务需要重新判断是否调度。命中规则时默认创建新的子 Agent，不自动恢复已关闭的 Agent。
4. 只有在仍保留原 `agent_id` 且明确需要原 Agent 上下文时，才调用 `resume_agent` 恢复；不得仅因任务名称相似就自动恢复。
5. Agent 仍在运行或等待暂时超时时，不得仅为清理而关闭；确需终止时，应说明未完成事项。

### 子 Agent 委派规范

主 Agent 需在传给子 Agent 的 `message` 或 `items` 中使用以下五项；每项只写完成任务所需的最小信息，不重复整段对话、系统规则或可直接读取的文件内容：

```text
任务目标：
成功标准：
约束情况：（含背景、输入、允许读写范围、禁止事项）
证据要求：
输出情况：（含结论、变更文件、阻塞项和未执行事项）
```

发起调度前，主 Agent 必须检查这五项是否覆盖当前任务；如果发现会影响任务执行、权限边界、成功判断、证据核验或结果回传的重要事项，应补充到最相关的字段中，不为形式完整而新增固定字段。某项不适用时明确写“不适用”，不得静默省略。上述内容必须出现在实际传给子 Agent 的任务中，不得只写在面向用户的多 Agent 调度回执里。
